# AeroChat: правила для агентов

Начните с [README](README.md) и [навигатора](docs/README.md), затем читайте только источники,
которые относятся к задаче. Команды, toolchain, runtime ownership и координация проверок —
[development](docs/development.md). Подробные обязательные стандарты перенесены в
[engineering-standards](docs/engineering-standards.md): перед изменениями прочитайте нужный
раздел по таблице в начале документа. Не загружайте все ADR, отчёты и test runbooks для каждой задачи.

## Инварианты, которые действуют всегда

- Монорепозиторий, Go-first backend, proto-first контракты. Изменения границ сервисов, storage,
  auth, crypto, transport, deployment, self-host, UI shell или фундаментальных зависимостей
  требуют ADR с контекстом, решением и последствиями. Контракты и generated code не копировать вручную.
- Не придумывать криптографический протокол, шифр или handshake. Следовать утверждённому
  ADR конкретной crypto lane; dev-заглушки не выдавать за production semantics. Не объявлять
  E2EE или безопасность реализованными без спецификации и проверок; текущие ограничения —
  [capabilities](docs/product/capabilities.md) и [project-status](docs/project-status.md).
- Media не превращать в постоянное plaintext storage на сервере. Не хранить пароли или
  секретный key material открытым текстом в БД/логах. Никогда не логировать пароли,
  access/refresh tokens, ключевой материал, plaintext сообщений/вложений, полные secrets из env
  и приватные профилирующие данные.
- Сохранять независимость frontend shell и backend domains. Бизнес-логика не живёт в transport
  handlers; не добавлять global mutable singleton state, скрытую DI/config/runtime магию или ad-hoc SQL.
- Shell остаётся лёгким, heavy UI загружается lazy. Не добавлять тяжёлую UI-библиотеку без
  обоснования, raw HTML rendering для Markdown или mobile UX regression ради desktop-эстетики.
- Одна задача — узкая ветка и PR. Не работать напрямую в `main`, не объединять несвязанные
  auth/crypto/storage/RTC/infra перестройки и не менять архитектуру «заодно». Сохранять чужие правки.
- Безопасность, корректность, простота и воспроизводимость выше производительности, DX и
  визуальной полировки. Конкретные TODO должны объяснять оставшийся результат и его ограничение.

## Перед изменением

1. Проверьте существующее решение, затрагиваемые файлы и принятый ADR своей области.
   Код показывает реализацию, а исторический аудит — только указанную в нём ревизию.
2. Выберите применимые [инженерные стандарты](docs/engineering-standards.md) и проверки из
   [development](docs/development.md). Сформулируйте scope и способ приёмки до существенной правки.
3. Для нового инструмента, config/integration flow или зависимости сверьтесь с актуальной
   официальной документацией. Не угадывайте изменяемые API и security-sensitive поведение.
4. Не меняйте deployment, retained data или чужой runtime ради локальной проверки. Для
   инфраструктурной задачи используйте её runbook, согласованный runtime owner и shared lock.

## Проверка и завершение

- Вопросы и аудиты без правок требуют исходных свидетельств, без запуска build/test/runtime.
- Изменения только документации проверяются по ссылкам, фактам, форматированию и `git diff --check`.
  Исполняемые примеры и файлы, поставляемые продуктом, требуют проверки реального поведения.
- Изменения поведения сопровождаются meaningful tests: доменная логика, критичные integration
  paths и подходящий smoke. Не снижать покрытие без причины, не скрывать skips/flaky failures,
  не заменять утверждения пустыми snapshots. Сначала релевантные проверки; полный candidate gate
  используется, когда этого требует scope или CI. Обязательные hosted checks не отключать.
- Для infra/runtime изменения проверить запуск своего compose scope, логи, readiness/health и
  отсутствие restart loop. Не коммитить secrets, дампы, caches или runtime-артефакты.
- Обновлять документацию вместе с изменённым поведением. Архитектурное решение документируется
  до реализации; не представлять предложенную или подготовленную возможность как подтверждённую.
- Перед PR проверить diff, отсутствие случайных файлов, форматирование и результаты выбранных
  проверок. Указать outcome, риски, проверенные команды/ревизию, непройденную приёмку и ADR, если нужен.
- Коммиты — краткие Conventional Commits; детали и примеры — в
  [стандартах](docs/engineering-standards.md#3-правила-коммитов). Внутренняя документация и полезные
  комментарии — на русском; сущности и имена пакетов — на английском. Не комментировать очевидное.
